    the problem

    Agents already hold the keys. Sometimes they use them.

    Most Docker MCP servers hand the agent the whole Engine API. If the agent can reach a destructive call, a confused plan or a stray token is all it takes.

    No route

    In Veklom Gate, deleting a volume is not a rule the agent is asked to follow. No code path reaches it. The agent never holds the Docker socket, and the one process that does has no volume route.

    three guarantees

    Useful at 3am. Harmless on its worst night.

    No route to destroy

    The gate is the only process with the Docker socket, and it answers seven requests: list, inspect, env-var names, logs, restart, stop and start. Exec, create, remove, volumes, images and archive are not there to call, so no prompt, policy bug or approval can reach them.

    From the live runevaluate_operation docker.exec, approved: true
    → risk_tier "forbidden", allowed false

    Approvals the agent can't forge

    Stop and start need an Ed25519 signature made off the server. Each approval names one deployment, one tool and the exact parameters. It expires quickly and works once. The server holds only the public key.

    From the live runsame approval, second use
    → "Approval token has already been consumed."

    Autonomy only with proven redundancy

    A restart runs on its own only when at least two replicas of the same Compose service are running and passing their health checks. A container with no health check never counts as healthy.

    shop-api-1, 1 replica → "approval_required"
    docker-compose.yml · docker_gate.py

    Two containers, and only one of them touches Docker.

    The MCP server decides whether an action may run. The gate decides what can run at all. Splitting them means a compromised or confused MCP process can still only do what the gate's routes allow.

    policy.py · four tiers

    Every action has a tier. Unknown actions fail closed.

    LOWAUTONOMOUS

    Read-only

    Runs without asking.

    • host info
    • list / inspect
    • env-var names
    • redacted log tail
    • health probes
    • audit verify
    MEDIUMIF PROVEN SAFE

    Reversible mutation

    Autonomous only when 2 or more replicas of the same Compose service are running and healthy. Otherwise it asks for approval.

    • restart_container
    HIGHSIGNED APPROVAL

    Consequential mutation

    Needs a one-time Ed25519 approval bound to this deployment, this tool and these exact parameters.

    • stop_container
    • start_stopped_container
    FORBIDDENNEVER

    Crosses a trust boundary

    Refused even with a valid approval.

    • exec
    • create / remove
    • delete volume
    • prune
    • read filesystems
    • raw socket
    • secret values
    • database writes
    • shell

    Your policy file can only make the model stricter. Forbid more, require approval more, or raise the replica floor. There is no key that allows, downgrades or un-forbids anything, and a file that tries fails at startup.

    policy.json · tighten only
    {
  "forbid": ["service.stop", "infra.logs.read"],
  "require_approval": ["service.restart"],
  "min_healthy_replicas": 3
}

    mcp_server/ · quick start

    One host, about five minutes.

    It starts read-only. Lifecycle actions stay off until you turn on two separate switches and give the server an approval public key.

    1. Opt a service in

      Only labelled containers are visible. Add a health check, and two replicas if you want restarts without a human.

      your docker-compose.yml
      services:
  web:
    image: example/web:1.4.2
    labels:
      veklom.ops.managed: "true"
    healthcheck:            # required for autonomous restarts
      test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
    deploy:
      replicas: 2           # two healthy replicas: restarts need no human

    2. Start the gate and the MCP server

      Fill in .env: an MCP access token, two different gate tokens, and the group id that owns the Docker socket.

      shell, on the Docker host
      git clone https://github.com/reprewindai-dev/veklom-ops-command
cd veklom-ops-command/mcp_server
cp .env.example .env
# VEKLOM_MCP_ACCESS_TOKEN, DOCKER_GATE_READ_TOKEN, DOCKER_GATE_ACT_TOKEN
# (e.g. openssl rand -hex 32, a different value for each)
# DOCKER_SOCKET_GID=$(stat -c %g /var/run/docker.sock)
docker compose up -d --build

    3. Connect your agent

      Expose the MCP through your TLS tunnel (Cloudflare Tunnel, for example) and set MCP_ALLOWED_HOSTS to that hostname. Then add it to your client.

      Claude Code
      claude mcp add --transport http veklom-gate https://ops.example.com/mcp \
  --header "Authorization: Bearer $VEKLOM_MCP_ACCESS_TOKEN"

    4. Turn on approvals, when you're ready

      Generate the keypair somewhere other than the server. Only the public key and a unique deployment name go on the MCP.

      on your own machine, then the server's .env
      veklom-mcp-keygen        # keep the PRIVATE key off the server

# server .env
VEKLOM_MCP_WRITES_ENABLED=true
VEKLOM_MCP_APPROVAL_PUBLIC_KEY_B64=<public key>
VEKLOM_MCP_APPROVAL_AUDIENCE=acme-prod
DOCKER_GATE_ALLOW_ACT=true

    Know before you run it

    • No production user yet. It has been verified end to end against a real Docker Engine, not run in anyone's production.
    • No external security review of the gate yet.
    • Inbound auth is a single static bearer token. Fine for one operator, not for a team.
    • Run one MCP replica per deployment. Approval nonces live on a local volume.
    • One gate per Docker host. Multi-host fleets need one stack per host for now.
    • The approver page is self-hosted. Push notifications and multi-person approval are not built yet.
    • Log redaction is best effort. For sensitive workloads, forbid log reads in the policy file.

    questions

    Straight answers.

    What if the gate itself is compromised?

    Then the attacker holds the Docker socket, which is root-equivalent on the host. That is the residual risk of this design, and we don't hide it.

    The mitigations are about size and reach. The gate is one small module. It runs non-root with a read-only filesystem and every capability dropped, sits on an internal network with no outbound route, publishes no port, and only answers token-authenticated routes. Treat every change to docker_gate.py as a privileged-code change. There has been no external security review yet.

    And if the MCP server is compromised?

    It can call the gate routes its tokens allow, on labelled containers. At worst that means restarting, stopping or starting them, and lifecycle calls also need the gate's own DOCKER_GATE_ALLOW_ACT switch. It can't exec, delete volumes, read env values or reach unlabelled containers, and it never holds the private key that mints approvals.

    Can the agent approve its own request?

    No. The server stores only the Ed25519 public key; the private key stays with you. Each approval is bound to one deployment, one tool, one action and the SHA-256 of the exact parameters. It expires quickly and is consumed on first use. In the live run, reusing an approval was refused, and presenting it for a different tool was refused too.

    Will my agent see secrets?

    Env values never leave the gate; the agent sees variable names only. Mounts, command arguments, health-check output and non-allowlisted labels are dropped too.

    Logs are capped and redacted, but redaction of free text is best effort: no regex catches every secret an application might print. For sensitive workloads, add "infra.logs.read" to forbid in your policy file.

    Is it ready for production?

    It has been verified end to end against Docker Engine 29.8 with a real MCP client, and has 137 automated tests. It has no production users yet and no external security review. Start read-only, on one host, and read the known limits above before enabling lifecycle actions.

    Which agents does it work with?

    It speaks MCP over Streamable HTTP and is built for Claude Code, Cursor, ChatGPT and other MCP clients. It also ships an Operator Evidence Panel that ChatGPT can render as an MCP App.

    Do I need Kubernetes or Swarm?

    No. It targets plain Docker and Docker Compose hosts. Today it is one gate per Docker host. Multi-host support and a Kubernetes adapter are planned, not built.

    What happens after an approved stop?

    Docker accepts a restart, stop or start before the container is healthy again, so the server reports what Docker accepted. Re-read the container with get_container and check its health probe before calling the change done. If the upstream call fails after the approval is verified, the approval is still spent and the response says so.
